# Сайт DeiX (Vercel)

Публичный сайт про DeiX, форма заявки на одноразовый токен dev-режима и
панель Owner. Без сборки и без зависимостей: статика в `public/` и две
serverless-функции в `api/` (Node 22).

| Путь | Назначение |
|---|---|
| `/` | о проекте |
| `/en`, `/en/<страница>` | английская версия каждой страницы (`/en/login`, `/en/account`, …) |
| `/register`, `/login` | регистрация (проверка адреса, письмо подтверждения) и вход (с шагом TOTP, если 2FA включена) |
| `/account` | обзор, устройства, dev-ключ, безопасность: подтверждение почты, 2FA с резервными кодами, смена пароля |
| `/verify?token=...` | подтверждение почты по ссылке из письма |
| `/request` | заявка на токен для привязанного устройства (только для вошедших) и «Мои заявки» |
| `/admin` | панель Owner (нужна сессия с 2FA): принять/отклонить/удалить заявку, приём заявок вкл/выкл |
| `POST /api/auth` | `config`, `me`, `register`, `login`, `logout`, `change_password`, `verify_email`, `resend_verification`, `mfa_verify`, `mfa_status`, `mfa_enroll_start`, `mfa_enroll_finish`, `mfa_disable`, `mfa_backup_regenerate` |
| `POST /api/os?fn=...` | шлюз для ОС: `begin_device_link`, `device_link_status`, `request_dev_unlock`, `claim_dev_unlock` |
| `POST /api/devices` | `list`, `link` (код из `dev link`), `unlink` |
| `POST /api/keys` | `list`, `issue` (офлайн-ключ `dev unlock` для Device ID; нужна переменная `DEV_KEY_PRIVATE`) |
| `POST /api/request` | `mine`, `submit` |
| `POST /api/admin` | `list`, `decide`, `remove`, `set_open` (только role=owner) |

Все POST требуют заголовок `X-DeiX-CSRF: 1` и same-origin. Сессия — cookies
`deix_at`/`deix_rt` (HttpOnly, Secure, SameSite=Strict, 30 дней) поверх
Supabase Auth.

Переменные окружения Vercel: `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET`
(без двух последних капча выключена). Схема и создание Owner описаны в
`docs/DEVAUTH.md`; тесты API: `npm test` (без сети, Supabase подменён).

Root Directory проекта Vercel — `web`.

## Почта и двухфакторная аутентификация

* **Проверка адреса при регистрации** работает всегда: домены одноразовой
  почты отклоняются, у домена должен быть MX (или A) в DNS. Сбой самого
  DNS-запроса адрес не отклоняет.
* **Письмо со ссылкой подтверждения** уходит, если заданы `MAIL_FROM` и
  один из ключей: `RESEND_API_KEY` (resend.com) или `BREVO_API_KEY`
  (brevo.com). Необязательная `SITE_URL` задаёт адрес ссылки (по умолчанию —
  хост запроса). Пока ключа нет, письма не отправляются и подтверждение
  ничего не блокирует; с ключом неподтверждённые аккаунты не получают
  dev-ключи и не подают заявки. Вход подтверждение не блокирует.
  Отправитель в Resend должен принадлежать подтверждённому домену, в Brevo —
  подтверждённому адресу отправителя.
* **Как включить письма** (Vercel → проект → Settings → Environment Variables, затем Redeploy):
  * Brevo (не нужен свой домен): подтвердите адрес отправителя в Brevo → Senders, создайте API-ключ (SMTP & API → API Keys) и задайте `BREVO_API_KEY` и `MAIL_FROM="DeiX OS <ваш@подтверждённый.адрес>"`.
  * Resend (нужен свой домен): подтвердите домен в Resend → Domains, создайте ключ, задайте `RESEND_API_KEY` и `MAIL_FROM="DeiX OS <noreply@ваш-домен>"`.
  * Необязательно: `SITE_URL=https://deix-sepia.vercel.app`.
  * Проверка: зарегистрируйтесь с настоящим адресом, откройте письмо, перейдите по ссылке `/verify?token=…`; в «Аккаунт» почта станет подтверждённой.
* **2FA (TOTP)** использует MFA Supabase Auth (в проекте включён TOTP).
  Вход: пароль → cookie `deix_mfa` (5 минут, только `/api`) → код →
  обычная сессия уровня aal2. Подключение и отключение — в «Аккаунт» →
  «Безопасность». 8 резервных кодов хранятся хэшами SHA-256; резервный код
  срабатывает один раз и отключает 2FA. Не больше 5 неверных кодов за
  10 минут на аккаунт.
* **Owner**: `/admin` и `POST /api/admin` требуют сессию aal2, иначе
  отвечают 403 с `code: "mfa_required"`.
* Миграция: `supabase/migrations/20261018100000_security.sql`.

## Какие данные где хранятся

Политика конфиденциальности — `public/privacy.html` и `public/en/privacy.html` (`/privacy`, `/en/privacy`); `test/privacy.test.js` проверяет, что в ней перечислены все cookie, ключи браузерного хранилища и таблицы из миграций. Меняете данные или поставщиков — обновите политику и таблицу версий в разделе 19.

**На сервере (Supabase):** почта, имя пользователя, роль и хэш пароля (его хранит Supabase Auth); служебное, без которого сайт не может защищаться: привязка устройств к аккаунту (`device_links`), заявки на токен (`dev_unlocks`: имя устройства и заметка адресованы владельцу проекта, поэтому остаются на сервере), хэши резервных кодов 2FA, токены подтверждения почты и счётчик выдач ключей (`dev_keys`: только `user_id` и время для лимита 5 в час).

**В браузере пользователя (`public/vault.js`):** имена устройств и история выданных dev-ключей.
- Данные лежат в `localStorage` одним блоком, зашифрованным AES-256-GCM; ключ выводится из пароля через PBKDF2-SHA256 (600 000 итераций, случайная соль), на сервер он не уходит. Блок привязан к id аккаунта, подмена или порча данных обнаруживается.
- Ключ создаётся при входе или регистрации и до выхода хранится в IndexedDB как неизвлекаемый `CryptoKey`: страницы сайта перезагружаются при каждом переходе, а вводить пароль на каждой странице нельзя. «Выйти» и потеря сессии удаляют ключ; данные остаются зашифрованными.
- При смене пароля в аккаунте блок перешифровывается новым паролем. Если пароль сменили в другом браузере, здесь данные останутся под старым: их можно открыть старым паролем или сбросить на странице «Аккаунт».
- Это обычное хранилище браузера: очистка данных сайта, другой браузер или другой компьютер означают пустое хранилище. Резервной копии на сервере нет по замыслу.
- Любой скрипт этого же origin, пока вы вошли, может воспользоваться ключом: защита — строгая CSP (`script-src 'self'`) и отсутствие внешних скриптов, кроме Turnstile.

Новые пользовательские данные, которым не нужно быть на сервере, добавляются в `Vault` (поля `keys`, `labels`), а не в таблицы.

## Версии ОС для скачивания

Owner добавляет готовые образы диска в `/admin` → «Версии ОС»; все посетители видят опубликованные на `/download`.

- Миграция `supabase/migrations/20261023120000_os_releases.sql` создаёт таблицу `os_releases` и приватный бакет `os-images` (применить один раз).
- Файл не проходит через функции Vercel (лимит тела 4,5 МБ): браузер считает SHA-256 и грузит файл прямо в Supabase Storage по одноразовой подписанной ссылке (`release_prepare`), затем сервер сверяет размер объекта (`release_finalize`). Расширения: `.img`, `.img.gz`, `.img.xz`, `.zip`, `.qcow2`.
- Предел размера — 50 МиБ (бесплатный тариф Supabase; на платном повышается в настройках Storage и в миграции).
- Скачивание: `GET /api/releases?download=<версия>` отдаёт 302 на подписанную ссылку на 5 минут и увеличивает счётчик; не более 30 скачиваний в час с одного адреса. Список опубликованных версий — `GET /api/releases`.
- Загрузка и скачивание идут напрямую на `*.supabase.co`: в сетях, где этот домен заблокирован, нужен VPN. Постоянное решение — свой домен для Supabase.
- Версия без загруженного файла остаётся черновиком (`ready = false`) и не видна на `/download`; повторная загрузка той же версии перезаписывает такую запись.

## Центр обновлений ОС и защита от потока запросов

- Миграция `supabase/migrations/20261023160000_os_updates.sql` создаёт `os_updates` (применить один раз); нагрузка лежит в том же приватном бакете `os-images` по пути `updates/<сборка>/payload.bin`.
- Owner загружает пакет из `build/update/` (манифест + нагрузка) в `/admin` → «Обновления ОС». Формат пакета и порядок обновления — `docs/UPDATE.md`.
- ОС берёт `GET /api/update?channel=stable` (манифест вставляется в ответ как текст, байт-в-байт: подпись считается по нему) и `GET /api/update?build=<N>&part=<K>` (куски по 128 КиБ: лимит ответа ОС — 1 МиБ). Подпись проверяет ОС; необязательная переменная `UPDATE_PUBKEY` (130 hex-символов публичного ключа) включает такую же проверку при загрузке пакета владельцем.
- Лимиты по адресу: манифест 120/ч, куски 600/ч, плюс общий потолок `FLOOD_MAX_PER_MINUTE` (300 запросов в минуту на все API). Счётчики живут в памяти одного экземпляра функции — это защита от одиночного шумного клиента. От распределённого потока защищает фильтр Vercel: Project → Firewall → **Attack Challenge Mode** (включается владельцем вручную; управлять им через API-коннектор нельзя). Страницы остаются открытыми, капча (Turnstile) стоит на регистрации и входе.
- Адрес для ОС — `deix-atimenkas-projects.vercel.app`: редирект на основной хост действует только для страниц, `/api/*` не перенаправляется (ОС не повторяет POST по `Location`).

## Настройки проекта Vercel

* Root Directory `web`, Output Directory `public`, Install/Build Command —
  заглушки `echo ...` (сборки нет; пресет Framework выбран `Vite` только
  ради этого: API Vercel не принимает первый деплой проекта без пресета).
* Deployment Protection → Vercel Authentication должна быть **выключена**,
  иначе `*.vercel.app` просит вход в Vercel и сайт недоступен посетителям.
* Первый деплой сделан из ветки `arena/5fde79b0-deix`; автодеплой по
  push включается в Settings → Git (Create deployments).

## Языки

Русская версия лежит в корне `public/`, английская — в `public/en/` с теми же
именами файлов и теми же `id` элементов (это проверяет `test/i18n.test.js`).
Язык страницы задаёт `<html lang>`.

* Тексты, которые рисует JavaScript, проходят через `tr('русский текст')` из
  `public/i18n.js`; английские варианты — в таблице `EN` там же. Ссылки между
  страницами — через `lp('/путь')`, он добавляет `/en` в английской версии.
* Переключатель RU / EN в шапке запоминает выбор в `localStorage`
  (`deix-lang`). Первый заход на `/` из браузера с английским языком
  перенаправляет на `/en`, пока выбор не сделан.
* API отвечает на языке заголовка `x-deix-lang` (его шлёт `postJson`):
  таблица в `api/_i18n.js` переводит поля `error` и `message`, а письмо
  подтверждения приходит на языке страницы, с которой была регистрация.
* Новое сообщение на русском без перевода ломает `npm test`.

## Оформление и сторонние библиотеки

Движение сайта (`public/motion.js`) использует GSAP + ScrollTrigger + SplitText, Lenis, vanilla-tilt, canvas-confetti и 3D-сцену на three.js (фиксированный фон: сфера, ядро, кольца, пыль; путь по странице зависит от прокрутки). Файлы лежат в `public/vendor/` (CSP не пускает внешние ресурсы), версии и лицензии — в `public/vendor/LICENSES.md`. Шрифты Inter и JetBrains Mono тоже локальные.

- Скрипты подгружаются по странице: админка и формы получают только GSAP; 3D-сцена (≈540 КиБ) — на главной, /download и страницах входа (там приглушена), при наличии WebGL; на слабых устройствах упрощается, а при `prefers-reduced-motion` рисуется один неподвижный кадр. Сцена сама отключается, если кадров меньше ~30 в секунду.
- При `prefers-reduced-motion` и без JavaScript сайт полностью работает без анимаций.
- После удачной заявки или привязки устройства вызывается `window.deixCelebrate()` (конфетти без Web Worker, из-за CSP).
- Пересборка 3D-сцены: `web/vendor-src/build.sh` (исходник — `web/vendor-src/hero3d.src.js`).

## Оформление (пятый проход)

Палитра — монохром и один красный акцент (`--accent`), тёмная и светлая темы. Строгая сетка без скруглений, крупные заглавные заголовки, карточки заливаются красным при наведении, красная бегущая строка и красный блок призыва, зернистость поверх страницы, огромный контурный «DEIX» в подвале. Все цвета заданы переменными в начале `public/style.css`; 3D-сцены берут `--accent` и `--accent-2` оттуда же.

Эффекты: «сканер» на 3D-сфере (красная полоса пробегает по точкам), подписи разделов проявляются из случайных символов, красная шторка при переходе между страницами (только при включённой анимации; сохраняется флаг в `sessionStorage`, без него шторка работает только на уходе), 3D-диск с «головкой чтения» рядом со стеком системы.

## 3D-стек системы

В разделе «Архитектура» на главной — интерактивная модель слоёв DeiX (загрузчик, ядро, /system, /userdata, dinit, рабочий стол): тянуть — вращать, наведение на слой или пункт списка выдвигает его. Рисуется той же `three-scene.js` (`DeixScene.mountStack`), создаётся лениво при подходе к разделу и останавливается вне экрана. Без WebGL остаётся список слоёв, при `prefers-reduced-motion` — статичный кадр.

## Нагрузка на Supabase

Сайт статический, оформление запросов к Supabase не добавляет. Чтобы не расходовать ресурсы базы зря:

- гость без cookie не вызывает Supabase вовсе (`me` отвечает сразу);
- ответ `me` для вошедшего кэшируется в памяти функции на 20 секунд и сбрасывается любым другим действием с аккаунтом;
- список релизов (`/api/releases`) и манифест обновления (`/api/update?channel=…`) отдаются с `s-maxage=60`, то есть CDN Vercel держит их минуту и повторные запросы до базы не доходят; всё остальное в `/api` по-прежнему `no-store`.
