# Формат исполняемых файлов DeiX — `.mex` (DeiX EXecutable)

Версия спецификации: 1.0 (соответствует DeiX v0.1)

## Зачем свой формат, а не ELF/PE

Мы сознательно не используем ELF или PE:
- В DeiX **нет пользовательского режима** — всё ядро и все программы
  выполняются в кольце защиты 0 (ring 0), в одном общем адресном
  пространстве. Полноценный загрузчик ELF с релокациями, per-process
  page tables, syscall-интерфейсом через `int`/`syscall` — это то, что
  нужно для настоящей многозадачности с изоляцией процессов, которой
  у нас пока нет и не заявлено как цель этого этапа.
- Загружать и исполнять ELF/PE «по-настоящему» (с релокациями, таблицами
  символов, PLT/GOT) — это отдельный большой проект (полноценный
  динамический линкер), нечестно было бы выдавать наполовину работающую
  реализацию за «поддержку ELF».
- `.mex` — это честное отражение реальной архитектуры DeiX: плоский
  бинарный код без релокаций, загружаемый по фиксированному адресу,
  вызываемый как обычная функция с указателем на таблицу системных
  функций ядра (аналог примитивного ABI, как в MS-DOS `.COM`-файлах,
  только чуть более структурированный).

## Модель исполнения

- Программа — это машинный код x86-64, скомпилированный/собранный без
  позиционно-независимого кода (не PIC), рассчитанный на загрузку по
  фиксированному виртуальному/физическому адресу `MEX_LOAD_ADDR =
  0x600000` (см. `src/mex.rs`).
- Ядро копирует тело программы (см. структуру файла ниже) по этому адресу
  и передаёт управление на `entry_offset` (смещение точки входа
  относительно начала тела, не относительно начала файла).
- Точка входа — обычная функция с сигнатурой (в терминах Rust/C ABI
  x86-64 System V, единственный аргумент передаётся в `RDI`):

  ```c
  int64_t mex_main(const MexApi* api);
  ```

  Возвращаемое значение (`RAX`) становится кодом возврата программы,
  который печатает команда `run`.
- Программа **не имеет собственного стека** — использует стек ядра
  (никакой изоляции процессов нет, это ring 0). Не должна оставлять
  мусор в регистрах, которые ожидает восстановленными вызывающий код
  (стандартный System V ABI: сохранять `RBX, RBP, R12-R15`).
- Программа обязана вернуться из `mex_main` (обычный `ret`) — у нас нет
  системного вызова `exit()`, завершение процесса означает просто
  возврат в `cli.rs::cmd_run`, которая печатает код возврата.

## Формат файла (бинарный, little-endian)

```
Смещение   Размер   Поле              Описание
0x00       4        magic             Байты 'M','E','X','1' (0x314D4558 LE)
0x04       2        version_major     Сейчас 1
0x06       2        version_minor     Сейчас 0
0x08       4        header_size       Размер заголовка в байтах (сейчас 32)
0x0C       4        entry_offset      Смещение точки входа от начала тела
0x10       4        body_size         Размер тела программы (машинного кода) в байтах
0x14       4        bss_size          Доп. память, обнуляемая после тела (аналог .bss)
0x18       8        reserved          Зарезервировано (0), для будущего расширения
0x20       ...      body              Машинный код + данные (body_size байт)
```

Всего заголовок — 32 байта (`0x20`), затем сразу тело.

Расширение файла: **`.mex`** (например, `hello.mex`). Хранится как обычный
файл на ext2-томе DeiX.

## Системный API (`MexApi`)

Единственный способ программе взаимодействовать с миром — таблица
функций, на которую указывает аргумент `api`. Структура (Rust):

```rust
#[repr(C)]
pub struct MexApi {
    pub print: extern "C" fn(ptr: *const u8, len: usize),
    pub read_char: extern "C" fn() -> u8,       // блокирующее чтение (hlt-loop)
    pub try_read_char: extern "C" fn() -> i32,  // -1 если пусто, иначе 0..255
    pub uptime_ms: extern "C" fn() -> u64,
    pub read_file: extern "C" fn(name_ptr: *const u8, name_len: usize,
                                  out_ptr: *mut u8, out_cap: usize) -> i64, // -1 ошибка, иначе длина
    pub write_file: extern "C" fn(name_ptr: *const u8, name_len: usize,
                                   data_ptr: *const u8, data_len: usize) -> i64, // 0 успех, -1 ошибка
}
```

Версионирование: поле `header_size`/`version_major` позволяет в будущем
добавлять новые функции в конец структуры, не ломая старые бинарники
(старые версии ядра просто не увидят новых полей, новые версии ядра
проверяют `version_major` перед вызовом новых функций).

## Ограничения (честно)

- **Нет защиты памяти.** Программа выполняется в ring 0 наравне с ядром
  — баг в программе (переполнение буфера, неверный указатель) может
  уронить всю систему, как в MS-DOS. Это прямое следствие отсутствия
  пользовательского режима в DeiX 0.1, а не недосмотр.
- **Нет позиционно-независимого кода.** Все `.mex`-файлы грузятся по
  одному и тому же фиксированному адресу — нельзя запустить два
  экземпляра одной программы одновременно (нет размещения на разных
  адресах), нельзя выполнять переиспользуемые библиотеки.
- **Нет аргументов командной строки в машинном виде** — `cli.rs`
  передаёт остаток командной строки после имени файла как обычную
  UTF-8 строку через `read_file`-подобный доступ (программа должна сама
  запросить их отдельным вызовом, будущее расширение API).
- Собираются такие программы вручную через `nasm` (или любой другой
  ассемблер/компилятор, способный дать плоский `.bin` без релокаций) +
  небольшой Python-скрипт `tools/mex_pack.py`, который добавляет
  32-байтный заголовок. Пример — `tools/hello.asm` +
  `tools/build_hello_mex.sh`.
