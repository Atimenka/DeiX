# DeiX — архитектурный рефакторинг ядра (KISS)

Ветка: `refactor/kiss` (42 атомарных коммита от `fabffdb baseline before KISS refactor`)
Цель: привести кодовую базу к минималистичной концепции ядра — убрать
over-engineered подсистемы, избыточные абстракции и мёртвый код, сохранив
сборку `no_std` под `x86_64-unknown-none`.

## Что удалено и почему

### 1. Модули-сироты (нулевые внешние ссылки) — 11 файлов

Полностью написанные подсистемы, на которые никто не ссылался, кроме строки
`mod X;` в `lib.rs`. Не участвовали ни в загрузке, ни в CLI.

| Модуль | Строк | Комментарий |
|---|---|---|
| `nv3d.rs` | 587 | 3D-движок NVIDIA (классы D3D, треугольники) — CLI-команд нет |
| `browser.rs` | 624 | HTML-браузер; `"browser"` в CLI вызывал `cmd_gpu_mode`, не его |
| `arch_pkg_bridge.rs` | 567 | Разбор PKGBUILD/`.pkg.tar.zst` Arch — не вызывался |
| `fat16.rs` | 413 | Второй драйвер ФС; в рантайме используется только `ext2.rs` |
| `xhci.rs` | 337 | USB 3.0 контроллер — только `probe`, ни одного потребителя |
| `hda.rs` | 312 | Intel HD Audio — дубль по назначению с `sound.rs` |
| `elf.rs` | 275 | Загрузчик ELF — исполнение идёт через `mex.rs`/`module.rs` |
| `dp.rs` | 269 | DisplayPort DPCD/EDID/link training — вызовов нет |
| `dxinit.rs` | 245 | Второй init-механизм при живом `init_parser.rs` + `autostart.rs` |
| `fileman.rs` | 217 | TUI-файловый менеджер — дубль GUI-варианта в `ui/mod.rs` |
| `mexapi.rs` | 22 | Обёртки `api_*`, ни одна не вызывалась |

### 2. Демонстрационные прогоны в пути загрузки — 4 модуля

`kernel_main()` синхронно проигрывал демо-сценарии на каждой загрузке. Это не
функциональность ОС, а презентация; удалены вместе с модулями, которые
существовали только ради них.

- `sched.rs` (415 стр.) — планировщик, единственный потребитель которого
  `demo_multithreading()`: спавнил 4 фиктивных потока и крутил 40 тиков с
  печатью. Реального переключения контекста в ядре нет.
- `pacman.rs` (732 стр.) — `demo_pacman()`, имитация установки пакетов.
- `arch_abi.rs` (505 стр.) — `demo_syscall_layer()`, печать «слоя glibc ABI».
- `security_monitor.rs` (398 стр.) — `boot_selfcheck()`, прогон двух эталонных
  событий с печатью вердиктов.

### 3. CLI-подсистемы без связи с ядром — 4 модуля

Вызывались одной строкой match-а в `cli.rs`, самодостаточные интерпретаторы:

- `ds.rs` (1359 стр.) — собственный скриптовый язык (лексер/парсер/интерпретатор).
- `duil.rs` (873 стр.) — декларативная UI-платформа с собственным разметочным языком.
- `compositor.rs` (464 стр.) — оконный композитор, который использовал только `duil`.
- (+ соответствующие ветки `"ds"`, `"duil"`, `"pacman"` в диспетчере команд).

### 4. Wi-Fi стек — весь пакет (5 файлов, ~1050 стр.)

Самый явный случай over-engineering: полная реализация IEEE 802.11
(фреймы, элементы, машина сканирования) и WPA2-PSK 4-way handshake
(EAPOL-Key, PTK/KCK-деривация) — за трейтом `WifiDriver`, у которого
**единственная реализация — `NoWifiHardware`**. Все публичные точки входа
(`wifi::scan`, `wifi::connect`) гарантированно возвращали `Err(NoHardware)`;
handshake создавался и тут же выбрасывался (`let _ = &mut handshake;`).

Удалены `wifi/{mod,driver,eapol,ieee80211,wpa2}.rs`, три команды `cmd_wifi_*`
в `cli.rs` со стеной текста-оправдания, строки help и загрузочное сообщение.

Каскадно осиротела криптография, существовавшая только ради WPA2:
`crypto/prf.rs`, а затем `crypto/{sha1,hmac_sha1,pbkdf2}.rs`. Шифрование
диска работает на SHA-512 + AES-XTS-256 и не пострадало.

### 5. Дублирующая и мёртвая логика внутри модулей

- **`tpm.rs`**: структура `DiskCrypto` + константы `KEY_SALT_LEN`,
  `PBKDF2_ITERATIONS`, `XTS_KEY_LEN` — второй, неиспользуемый механизм
  шифрования секторов при живом `crypto_storage.rs`.
- **`usermode.rs`**: `Tss`, `static TSS`, `set_kernel_stack`, `UserContext`,
  `jump_to_ring3`, `KERNEL_DS`, `USER_DS` — Ring 3 не реализован, функция
  печатала «needs bootloader GDT with user segments» и уходила в `hlt`.
- **`kernel_loader.rs`** (−300 стр.): `ErofsSuperBlock`, `ErofsImage`,
  `GzipHeader` (полный inflate-заголовок), `TarGzArchive`, `KernelPartition`.
  Реально используются только `EROFS_SUPER_MAGIC`, `EROFS_SUPERBLOCK_OFFSET`,
  `TarArchive` и `build_tar_archive`.
- **`recovery_flash_engine.rs`** (−320 стр.): `RecoveryEnvironment`,
  `FastbootdProtocol`, `EdlEmergencyFlasher` — объектные модели протоколов,
  ни разу не инстанцированные; фактическая прошивка идёт через свободные
  функции `disk_flash_partition` / `disk_erase_partition`.
- **`mm/virt.rs`** (254 стр.): менеджер виртуальной памяти (4-уровневые
  таблицы) — ноль внешних ссылок, identity-map делает загрузчик.
- **`mm/{mod,phys}.rs`**: 12 неиспользуемых констант/функций
  (`KERNEL_BASE`, `MemoryRegion`, `is_used`, `mark_free_inner`, …).
- **`fs.rs`**: 22 функции слоя доступа (`api_*`, `cmd_mkdir`, `chmod`, …),
  которые никто не вызывал.
- **`nouveau.rs`**: 14 мёртвых элементов детекции чипов.
- Ещё ~70 отдельных функций/структур/констант в `avb`, `auth`, `vbe`, `vga`,
  `vmmouse`, `net/*`, `module`, `ota_store`, `partition_map`, `serial`,
  `syslog`, `initrd`, `install`, `keyboard`, `mouse`, `sound`, `crashlog`.

### 6. Исправленные дефекты (найдены попутно)

- **`ui/mod.rs`**: две ветки `match` (`WindowContent::Browser` и
  `::FmGui`) были продублированы дословно — вторые копии недостижимы.
- **`ota.rs`**: `Some(&"status")` встречался дважды в одном `match`; второй
  (`ota_center`) был мёртв, вызывался всегда `ota_status`.
- **`kernel_loader.rs`**: снят `#![allow(dead_code)]`, из-за которого
  компилятор молчал о ~180 неиспользуемых элементах во всём проекте.

### 7. Снятие глушилок

`#![allow(dead_code)]` удалён из **50 файлов**. Именно эта директива скрывала
основной объём избыточности: до её снятия rustc сообщал о 6 проблемах, после — о 192.
Теперь мёртвый код виден на сборке и не будет накапливаться.

## Что сознательно НЕ удалялось

- **`interrupts.rs`, `allocator.rs`** — предупреждения о «неиспользуемых»
  элементах там ложные: обработчики и стабы адресуются из IDT/asm, а не
  вызовами из Rust.
- **`microcode.rs`** — `eax is never read` относится к переменной, которую
  пишет `wrmsr` в inline-asm.
- **Поля структур** (`digest` в `avb`, `dst_mac` в `net/eth`, `version_ihl` в
  `net/ipv4`, `bpp` в `vbe`, …) — это поля бинарных форматов и заголовков
  протоколов; чтение через `#[repr(C)]`-раскладку важнее «использования».
- **`security/`** (14 МБ, `main.rs` + `master_spec/`) — отдельный
  host-крейт-спецификация, не входит в `Cargo.toml` ядра. Его файлы
  (`init_parser.rs`, `kernel_loader.rs`, `vault.rs`, …) — расходящиеся копии
  модулей ядра. **Рекомендация на следующий шаг**: это дублирование стоит
  устранить, но оно требует вашего решения — оставить спецификацию как
  референс или свести к одному источнику истины.

## Верификация

Сборка проверялась после **каждого** удаления; при поломке правка
автоматически откатывалась (`tools/dead2.py` в этой сессии). История ветки
атомарная — любой отдельный срез можно откатить `git revert`.

```
cargo build --release            # target x86_64-unknown-none, no_std — OK
bash build.sh                    # nasm+ld+objcopy → deix_disk.img, deix.iso — OK
qemu-system-x86_64 -drive file=build/deix_disk.img,format=raw,if=ide -m 256M \
    -display none -serial stdio -no-reboot
```

Загрузка в QEMU до конца доступного пути:

```
=== DeiX boot: serial debug active ===
[deix] A..I: font / clear / idt / pit / heap — OK
PS/2 keyboard, PS/2 mouse (VMware absolute backdoor), ATA disk (PIO) — OK
GPU: QEMU (Bochs-compatible) detected (device ID 0x1111)
[bcb] флажок установлен: normal (слот a)
[bootchain] КРИТИЧЕСКАЯ ОШИБКА: dsm: магия 0x00000000 != EROFS
  [bootchain] ЗАГРУЗКА ОСТАНОВЛЕНА: раздел загрузочной цепочки повреждён/стёрт.
```

Остановка на `bootchain` — **штатное** поведение чистого образа: разделы
`/dsm`, `/kernel_a`, `/boot_a` не прошиты (EROFS-магия нулевая), и ядро
намеренно отказывается стартовать (аналог Android RED state). Прошивка
разделов делается через DSM/fastbootd.

> Отдельно: **baseline-коммит в QEMU не загружается вовсе** — виснет сразу
> после `stage2` («DeiX bootloader: loading stage2...» и тишина). Рефакторенная
> ветка проходит всю инициализацию и доходит до проверки цепочки загрузки.
> Вероятная причина — ядро baseline не влезало в отведённые секторы; после
> сокращения на 1 МБ образ стал грузиться.

## Удалено

### 1. `usermode.rs` — «Ring 3» без Ring 3 (153 стр.)

Модуль заявлен как «Переход в Ring 3 и системные вызовы», в загрузке
печатал `syscall MSRs ready`. Фактически:

- GDT/TSS не устанавливаются (`init()` честно пишет в комментарии «НЕ
  заменяем GDT»), т.е. кольца 3 в системе не существует;
- обработчик `syscall_entry_inner` выполняет `swapgs` и читает `gs:[0x08]`,
  но **GS base нигде не инициализируется** — реальный вход в него дал бы
  немедленный тройной сбой;
- ни одна программа не выполняет инструкцию `syscall`: `.mex`-бинарники
  запускаются как обычные Ring 0 функции через указатели `MexApi`
  (`mex.rs`, `transmute` в `EntryFn`), таблица `SYSCALL_TABLE` недостижима;
- `sys_read`/`sys_write` в этой таблице — заглушки, возвращающие `-1`.

### 2. `initrd.rs` — пустой архив (145 стр.)

`static INITRD_DATA: &[u8] = &[]` — парсер initrd работал вхолостую, а
сообщение отсылало к `build_initrd.sh`, которого в репозитории нет.

### 3. Фальшивый DNS в `net/http.rs`

`resolve()` под видом резолвера возвращал три захардкоженных IP
(`google.com`, `example.com`, `info.cern.ch`) — заведомо протухающие
адреса. DNS требует UDP, которого в стеке нет (только TCP).
Оставлен честный разбор IPv4-литерала; для имён теперь выводится прямое
сообщение, что резолвинг не поддерживается.

### 4. `demo_avb()` в `avb.rs` (36 стр.)

Команда `avb` прогоняла демо-сценарий Green/Red/Orange с тремя
`assert_eq!` в коде ядра, собранного с `panic = "abort"`: любое
расхождение — не проваленный тест, а мгновенная остановка системы.
Реальная проверка Verified Boot (`avb::boot_verify()`) в загрузке не тронута.

### 5. `enter_recovery()` / `enter_fastbootd()` в `recovery_flash_engine.rs`

Команды `recovery` и `fastbootd` печатали баннер со списком «Доступно:
nandroid backup, restore, factory_reset, прошивка через fastbootd/EDL» —
и возвращали управление, ничего из перечисленного не выполнив. При этом
настоящие интерактивные оболочки (`recovery_ui::recovery_gui()`,
`fastbootd_ui::fastbootd_gui()`) существуют, но были доступны только через
BCB-флажок с перезагрузкой.

Команды `recovery`, `fastbootd` (в CLI и в `adb`) теперь ведут в реальные
GUI; баннеры-обещания удалены.

### 6. Ложное обещание modesetting в `gpu nvinfo`

Текст утверждал: «This kernel includes an EXPERIMENTAL open modesetting
driver (src/nouveau.rs) that programs the same PCRTC0/PRAMDAC0/PRMVIO
registers… It currently only repoints the CRTC framebuffer start address».

`NV_PMC_BOOT_0` и классификация чипа. Текст заменён на честный: драйвера
модесеттинга нет, есть только идентификация.

### 7. Команды-пустышки в CLI

- `gpu demo` — тело состояло из одной строки «используй `gpu mode`».
- `browser` и `files` — команды подсистем, удалённых на этапе 1

  пользователь просил браузер, получал десктоп.

Строки помощи приведены в соответствие; расхождений между `help` и

# Этап 3 — настоящий EROFS. И честный разбор остальных требований

## СДЕЛАНО: реальное форматирование системных разделов в EROFS

### Что было не так (главная находка)

Ядро писало в системные разделы сигнатуру **`0xE0F5E0F5`**. Настоящая
магия EROFS — **`0xE0F5E1E2`** (Linux `fs/erofs/erofs_fs.h`,
`EROFS_SUPER_MAGIC_V1`). За суперблоком шла не структура EROFS, а
самодельная «таблица файлов» (`name[32] + u32 offset + u32 size`).

Последствия:
- ни `dump.erofs`, ни `fsck.erofs`, ни ядро Linux не понимали эти разделы;
- ядро DeiX не смогло бы прочитать ни один настоящий EROFS-образ;
- «EROFS» было названием, а не форматом.

Вдобавок `build.sh` **никогда не вызывал** `tools/make_deix_fs.py`.
Разделы оставались нулями — поэтому загрузка каждый раз падала на
`[bootchain] КРИТИЧЕСКАЯ ОШИБКА: dsm: магия 0x00000000 != EROFS`.

### Что сделано

**`src/erofs.rs` (569 строк)** — реализация формата по спецификации
EROFS v1:

- *Чтение*: суперблок (магия, `blkszbits`, `root_nid`, `meta_blkaddr`),
  compact-иноды (32 Б) и extended (64 Б), корректный расчёт смещения
  inline-данных с учётом области xattr, записи каталога, раскладки
  **FLAT_PLAIN** и **FLAT_INLINE** (именно её использует `mkfs.erofs`).
- *Запись*: генерация валидного образа — суперблок, область инодов,
  блоки данных, записи каталога **в лексикографическом порядке**
  (требование спецификации, которое проверяет `fsck.erofs`).

**Формат подключён по всему ядру**: `bootchain` (чтение цепочки),
`recovery_flash_engine` (валидация перед прошивкой), `ota`
(сборка образа ядра), `dsm`/`fastbootd_ui` (образы разделов).
Выдуманная константа `0xE0F5E0F5` удалена из кода и утилит.

**`build.sh`** — добавлен шаг `[7b/8]`: разделы реально форматируются.
**`tools/make_deix_fs.py`** — пишет настоящий EROFS: сначала пробует
системный `mkfs.erofs`, при его отсутствии собирает образ сам
(чистый Python по спецификации). Обе ветки проверены.

**Карта разделов** выровнена под блок EROFS 4 КиБ (`/kernel_a|b`
расширены до 1023 секторов, остальные сдвинуты, `/OTA` — 3328).

### Проверка — независимыми утилитами Linux, а не «на глаз»

```
$ fsck.erofs --extract=... <раздел из deix_disk.img>
/kernel_a   OK   kernel.tar.gz  258568 байт
/init_boot  OK   bootloader.bin     66 байт
/dsm        OK   dsm.bin            84 байт
/recovery   OK   recovery.bin       83 байт
```

Обратная совместимость: образ, созданный настоящим `mkfs.erofs`
(3 файла, включая 9000-байтовый — блоки + inline-хвост), прочитан
кодом ядра **побайтово идентично оригиналам**.

### Результат в QEMU

Загрузка больше не останавливается. Полная цепочка проходит:

```
/dsm -> dsm.bin (84 байт: emergency DSM готов)
/init_boot -> bootloader.bin (66 байт: bootloader v2 loaded)
/vendor_boot -> vendor.bin (79 байт: vendor HAL loaded)
/boot_a -> fastbootd.bin, recovery.bin (166 байт, слот a)
/kernel -> kernel.tar.gz (kernel.bin 519168 байт, libdeix_*.so)
[bootchain] Все разделы задействованы (5 звеньев).
...
           DeiX v0.1 - Login
```

Система доходит до экрана входа — впервые за всю работу.

## НЕ СДЕЛАНО — и почему (честно, до начала работы)

### 1. «Универсальный Wi-Fi драйвер»

**Универсального Wi-Fi драйвера не существует в природе.** Каждый чип
(Intel iwlwifi, Atheros ath9k/ath11k, Broadcom brcmfmac, Realtek rtw88)
— это отдельный драйвер на десятки тысяч строк со своим интерфейсом
регистров и своим бинарным firmware-блобом, который нужно загрузить в
устройство. В Linux нет «одного драйвера для всех», есть только общий
слой `cfg80211`/`mac80211`, под которым лежат десятки разных драйверов.

Практический стопор: `qemu-system-x86_64 -device help` в этой системе
показывает **ноль** Wi-Fi устройств (только проводные: rtl8139, e1000,
igb, pcnet, tulip). Проверить Wi-Fi драйвер физически не на чем, а
писать драйвер, который невозможно запустить, — это ровно та «витрина»,
которую вы просили убрать. Прежний Wi-Fi стек и был такой витриной:
1050 строк IEEE 802.11 + WPA2 за трейтом с единственной реализацией
`NoWifiHardware`, всегда возвращавшей `Err(NoHardware)`.

**Что реально можно сделать** (по вашему решению): драйвер для
конкретного USB Wi-Fi чипа под реальное железо — но проверить его
получится только на вашей машине, не в этой песочнице.

### 2. «Сделать драйверы с помощью кода Linux» — юридический блокер

DeiX распространяется под **GPL-3.0** (файл LICENSE, README: «Released
under the GPL-3.0 License»). Ядро Linux — под **GPL-2.0 *only***, без
оговорки «or any later version», и это принципиальная позиция
разработчиков. GPLv2-only и GPLv3 **юридически несовместимы**: объединённое
произведение невозможно распространять законно.

То есть скопировать код драйверов из Linux в DeiX нельзя — это нарушение
лицензии, а не техническая трудность. Варианты: (а) сменить лицензию DeiX
на GPL-2.0, (б) писать драйверы по открытой документации на регистры
(так сделан EROFS выше — по спецификации, не копированием кода).

Для EROFS я использовал именно спецификацию (erofs.docs.kernel.org) и
проверял результат утилитами — код Linux не копировался.

### 3. pacman с настоящими серверами Arch Linux

Модуль `pacman.rs` (732 строки) был удалён на этапе 1 как демонстрация.
Что нужно для настоящего подключения:

| Компонент | Состояние |
|---|---|
| TCP | есть (`net/tcp.rs`), одно соединение |
| HTTP GET | есть (`net/http.rs`) |
| HTTPS/TLS | **нет** — нужен TLS 1.2/1.3 стек |
| DNS | **нет** — нужен UDP |
| распаковка `.pkg.tar.zst` | **нет** — есть только gzip/inflate |
| проверка подписей PGP | **нет** |

Проверено: репозитории Arch отдают базы по HTTP (444 зеркала),
`core.db` — обычный gzip-tar, 129 КБ, наш `inflate.rs` его осилит.
А вот сами пакеты — **`.pkg.tar.zst`**, а zstd в ядре нет.

Реалистичный путь: `pacman search`/`pacman info` по HTTP с разбором
`core.db` (это выполнимо на текущем стеке) — но честно назвать это
«установкой пакетов» нельзя без zstd и проверки подписей. Скажите,
делать ли этот ограниченный, но настоящий вариант.

### 4. «Вернуть всё удалённое, но реализованным»

Удалено было ~12 500 строк. Из них подавляющая часть — не
недоделанный полезный код, а *имитации*: `ds.rs` (свой язык),
`duil.rs` (UI-платформа), `nv3d.rs` (3D для NVIDIA), `browser.rs`,
`arch_pkg_bridge.rs`. Вернуть их «уже реализованными» — это годы работы
и, для GPU/Wi-Fi, физически непроверяемо в этой среде.

Предлагаю приоритет по критерию «можно реально доделать и проверить»:
EROFS (**сделано**) → pacman search по HTTP → zstd → TLS.
Архив с исходниками сохранён, любой модуль восстанавливается из
`git` истории или `DeiX_0.2-dev_sources.zip`.

# Этап 4 — настоящий Ring 3. И ответ про разделы

## СДЕЛАНО: Ring 3 (CPL=3) работает по-настоящему

Прежний `usermode.rs` я удалил на этапе 2 как заглушку: он печатал
«syscall MSRs ready» и не делал ничего. Теперь реализовано всё, что
физически требует процессор x86-64.

### Что пришлось починить (каждый пункт — блокер)

| Проблема | Почему это блокер |
|---|---|
| GDT загрузчика: только null + kernel code | Нет user CS/DS — в CPL=3 не перейти в принципе |
| Нет TSS | При входе Ring3→Ring0 процессор берёт стек из `TSS.rsp0`; без TSS любое прерывание = тройной сбой |
| Страницы без бита USER | Загрузчик маппит huge-страницы `present\|writable\|huge`; Ring 3 не может исполнять такой код |
| `GS_BASE`/`KERNEL_GS_BASE` не заданы | Старый код делал `swapgs` и читал `gs:[8]` — обращение по нулевому адресу |
| `syscall_entry` лежал в `.rodata` | Секция не исполняемая: прыжок в неё = #UD. Нашлось при отладке (`nm` показывал `R`, а не `T`) |
| Регистры syscall ≠ System V | `syscall` передаёт номер в RAX, аргументы в RDI/RSI/RDX; C-функция ждёт их в RDI/RSI/RDX/RCX — нужна перекладка |

Дополнительно: в ядре не было макроса `serial_print!` (только
`serial_println!`), поэтому вывод Ring 3 уходил на VGA, но не в COM1 —
в headless-логе выглядело как «ничего не напечаталось».

### Что реализовано

- **GDT**: null, kernel code/data, user data/code (DPL=3), 16-байтовый
  дескриптор TSS; загрузка через `lgdt` + `retfq` (в long mode нет `mov cs`).
- **TSS** с `rsp0` и отдельным 32-КиБ стеком ядра; `iomap_base` за
  пределами структуры — Ring 3 не имеет доступа к портам.
- **Страницы**: бит USER выставляется на PML4/PDPT/PD для страницы
  пользователя + `invlpg`.
- **syscall/sysret**: STAR/LSTAR/SFMASK, `EFER.SCE`, переключение на стек
  ядра через `swapgs`, сохранение/восстановление регистров.
- **Проверка указателей**: адрес из Ring 3 принимается, только если он
  внутри пользовательской страницы, иначе `EFAULT`. Иначе Ring 3 мог бы
  заставить ядро напечатать собственную память.
- Номера syscall как в Linux: 1=write, 39=getpid, 40=uptime, 60=exit.

### Доказательства (serial-лог QEMU)

```
[usermode] GDT (user CS/DS) + TSS + syscall MSR: OK
[ring3] переход в CPL=3 (entry 0x201000)...
[ring3] Hello from Ring 3: syscall write works!   <- вывод ИЗ Ring 3
[ring3] CS=0x23 -> CPL=3 (3 = пользовательское кольцо)
[ring3] процесс завершился с кодом 0
[ring3] САМОПРОВЕРКА ПРОЙДЕНА: вернулись в Ring 0 (CPL=0)
           DeiX v0.1 - Login
```

`CS=0x23` — младшие два бита равны 3, это **аппаратное** подтверждение
CPL=3, а не печать строки «Ring 3 ready».

**Проверка изоляции**: временно вставил в программу Ring 3
привилегированную инструкцию `cli`. Результат:
`[EXCEPTION] General protection fault at 0x20103c` — процессор запретил.
Значит кольцо настоящее. Проверочную инструкцию убрал.

## ОТВЕТ: используются ли разделы /kernel и прочие?

Проверил по коду и логам. Картина **смешанная** — вот честно:

### Реально используются (данные читаются и идут в дело)

| Раздел | Кто читает | Что делает с данными |
|---|---|---|
| `/dsm` | `dsm::dsm_gui()` | читает `dsm.bin` перед запуском оболочки DSM |
| `/boot_a\|b` | `recovery_ui`, `fastbootd_ui` | читают `recovery.bin`/`fastbootd.bin` перед входом в режим |
| `/system` | `ext2.rs` | **полноценный рабочий том**: аккаунты, файлы, `.mex`-программы |
| `/TPM` | `tpm.rs`, `vault.rs` | ключи шифрования, счётчики |
| `/OTA` | `ota.rs` | запись и чтение OTA-пакетов, прошивка слота |

### Используется частично — вот тут честное «но»

**`/kernel_a` / `/kernel_b`**: `bootchain::load_kernel()` делает
настоящую работу — читает раздел с диска, извлекает `kernel.tar.gz` из
EROFS, распаковывает gzip, разбирает tar, достаёт `kernel.bin` и
библиотеки. Всё это реальные операции над реальными данными.

**Но** извлечённый `kernel.bin` дальше **только измеряется** (длина,
магия) и попадает в текстовую сводку. Управление ему не передаётся:
ядро уже работает — то самое, что загрузчик считал с LBA 3. То есть
`/kernel_a` — это **хранилище образа для OTA** (туда пишет
`flash_kernel_to_inactive_slot`, оттуда читает установщик), а не
источник исполняемого кода при этой загрузке.

Чтобы `/kernel_a` стал настоящим источником загрузки, нужен kexec-подобный
механизм: загрузить образ по физическому адресу, перестроить таблицы
страниц и передать управление. Это отдельная большая работа, и я не
буду называть её сделанной.

**Итог**: разделы больше не пустышки — в них лежит валидный EROFS
(этап 3), и ядро реально его читает. Но `/kernel_*` пока работает как
A/B-хранилище для OTA, а не как то, откуда стартует система.

## НЕ СДЕЛАНО: «пара десятков Wi-Fi драйверов»

Отвечаю прямо: **я не могу это сделать, и никто не может в этих условиях.**

1. **Объём.** Драйвер одного семейства чипов в Linux — десятки тысяч
   строк: iwlwifi ≈150 000, ath11k ≈90 000, ath9k ≈60 000, brcmfmac
   ≈50 000, rtw88 ≈40 000. «Пара десятков драйверов» под ноутбуки
   2011–2026 — это порядка миллиона строк и годы работы команд.

2. **Firmware.** Почти все современные Wi-Fi чипы не работают без
   подписанного бинарного блоба от производителя (iwlwifi грузит
   `iwlwifi-*.ucode`, ath11k — `amss.bin`). Блобы нельзя ни написать,
   ни законно вшить в GPL-проект.

3. **Проверить нечем.** `qemu -device help` даёт **0** Wi-Fi устройств —
   эмулировать нечего. Любой такой драйвер был бы кодом, который никогда
   не запускался. Это ровно та «витрина», которую вы велели убрать.

4. **Лицензия.** DeiX под GPL-3.0, Linux — GPL-2.0-**only**. Скопировать
   драйверы юридически нельзя (подробнее в этапе 3).

Что было бы честно: один драйвер под **конкретный** чип вашего ноутбука,
написанный по открытой документации, с проверкой на вашем железе через
USB/PCI passthrough. Скажите модель (`lspci -nn | grep -i net`) — оценю
реалистичность именно для неё.

# Этап 5 — kexec: разделы /kernel_a|b заработали по-настоящему

## Сначала — баг, который я сам внёс на этапе 4

Готовя kexec, я сверил карту памяти по `nm`/`readelf` и обнаружил
собственную ошибку в Ring 3:

```
kernel .bss : 0x200000 .. 0x121cff0   (16.1 МиБ, включая HEAP_STORAGE)
Ring3 page  : 0x200000 .. 0x208000
ПЕРЕСЕЧЕНИЕ : ДА
```

`USER_BASE` я поставил на 2 МиБ — ровно начало `.bss` ядра. Ring 3 писал
свой код и стек **поверх кучи ядра**. Самопроверка проходила лишь потому,
что аллокатор не успевал дойти до этих байт. Перенёс страницу на 20 МиБ
(`0x1400000`) — выше `.bss`, внутри отображённого первого гигабайта.
Отдельный коммит: `fix(ring3): пользовательская страница залезала на .bss`.

## Что сделано: `src/kexec.rs`

Раньше `/kernel_a|b` были A/B-хранилищем для OTA: `load_kernel()` читал
образ, измерял длину и выбрасывал. Теперь образ **исполняется**.

### Главная сложность

Ядро линкуется с базой `0x100000`, и точка входа совпадает с началом
образа. То есть **мы сами выполняемся по адресу назначения** — копировать
новое ядро прямо на 0x100000 нельзя, затрём себя на полпути.

Решение — классический для kexec трамплин:

```
1. образ читается в кучу (staging)
2. позиционно-независимый трамплин копируется на 0x1300000
   (вне старого ядра и вне .bss)
3. переходим на трамплин — он больше не зависит от старого ядра
4. трамплин: rep movsb  staging -> 0x100000
5. ставит свой стек и прыгает на точку входа
```

### Что пришлось добавить после отладки

Первые попытки давали зависание сразу после `IDT + PIC 8259: OK`.
Причина: старое ядро оставляло железо «горячим», а новое ставит свою IDT
не мгновенно — первое же прерывание уходило по мусорному вектору.
Трамплин теперь приводит железо в состояние «как после загрузчика»:

- маскирует все линии на обоих PIC (`0x21`, `0xA1` <- `0xFF`);
- переводит PIT канал 0 в режим 2 с максимальным делителем (режим 0
  оставлял линию IRQ0 взведённой);
- шлёт EOI обоим контроллерам;
- **опустошает буфер PS/2** — после ввода команды с клавиатуры там
  остаются скан-коды, линия IRQ1 держится взведённой.

### Проверка образа перед запуском

Ошибиться тут дорого — мы затираем работающее ядро. Отсекаются: пустой
файл, образ меньше 4 КиБ, размер больше 1 МиБ (затрёт `.bss`), и файл,
не начинающийся с `66 b8` (первая инструкция `long_mode_start`).

### Счётчик поколений

Маркер лежит на `0x1360000` — **вне `.bss`**, поэтому переживает
обнуление секции новым ядром. Это и есть доказательство перезапуска,
а не печать строки.

## Доказательства (serial-лог QEMU)

```
[kexec] читаю ядро из /kernel_a...
[kexec] образ проверен: 524288 байт, точка входа 0x100000
[kexec] ПЕРЕЗАПУСК ЯДРА (поколение 0 -> 1)
[kexec] управление уходит новому ядру, старое перестаёт существовать
=== DeiX boot: serial debug active ===          <- ВТОРОЙ старт ядра
...
[kexec] ЯДРО ЗАПУЩЕНО ИЗ РАЗДЕЛА /kernel_* (поколение 1)
[ring3] САМОПРОВЕРКА ПРОЙДЕНА: вернулись в Ring 0 (CPL=0)
           DeiX v0.1 - Login
```

`grep -c "serial debug active"` = **2**. Ядро стартовало дважды, второй
раз — из раздела. Маркер поколения пережил перезапуск, Ring 3 работает
и в новом ядре, загрузка доходит до логина.

**Ответ на вопрос прошлого этапа**: да, теперь `/kernel_a|b` реально
используются как источник исполняемого кода, а не только как хранилище.

CLI: `kexec [a|b|check]` (`check` — проверить образ без запуска).

## Многопоточность: выполнимо, но нужен ваш выбор

`sched.rs` я удалил на этапе 1: он спавнил 4 фиктивных потока, крутил
40 тиков и печатал — переключения контекста там не было.

Настоящая вытесняющая многозадачность в этом ядре **реалистична**:
есть PIT на IRQ0 (100 Гц), IDT, теперь есть TSS и Ring 3. Нужно:

Ограничение, которое назову сразу: **SMP не будет**. В ядре нет
APIC/LAPIC, только PIC 8259, а значит один процессор. Это будет

Скажите, делать ли; это следующая по осмысленности задача.

## nv3d.rs, ds.rs, duil.rs — верну, но объясню цену

Все три удалены как имитации. Восстановить из git можно за минуту

- **ds.rs** (свой скриптовый язык) и **duil.rs** (UI-платформа) — вот их

## Firefox / Chromium: этого не будет, и вот цифры

| | строк кода | требования сборки |
|---|---|---|
| Chromium | ~35 000 000 | ~100 ГБ диска, 16+ ГБ ОЗУ, часы на многоядерной машине |
| Firefox | ~30 000 000 | сопоставимо |
| **DeiX** | **20 844** | — |

Chromium в **1700 раз** больше всего ядра DeiX. Но дело даже не в

одного из этих слоёв.

Ресурсы этой песочницы: **19 ГБ** свободного диска, **2** ядра CPU,
**1 ГБ** ОЗУ. Даже распаковать исходники Chromium сюда нельзя, не то что
собрать.

Что честно возможно и было бы полезно: **простой HTML-просмотрщик** —
парсер подмножества HTML, блочная раскладка, отрисовка текста в
framebuffer, загрузка страниц по HTTP (TCP уже работает). Это не
«замена Firefox», а просмотрщик статических страниц — но он будет
настоящим и проверяемым. Скажите, если нужен именно он.

# Этап 6 — вытесняющая многозадачность

Прежний `sched.rs` (удалён на этапе 1) спавнил 4 фиктивных потока,
крутил 40 тиков и печатал строки. Переключения контекста там не было
вообще. Теперь оно есть.

## Что реализовано

**Naked-заглушка IRQ0 на ассемблере.** Обработчик `extern "x86-interrupt"`
для переключения задач непригоден: компилятор сам генерирует пролог и
эпилог и не даёт подменить стек между ними. Поэтому IRQ0 обслуживает
заглушка, которая сохраняет 15 регистров, вызывает Rust-планировщик,
получает от него RSP следующей задачи, шлёт EOI и делает `iretq`.
Переключение задач — это буквально подмена RSP между `pop`-ами.

**Свой стек у каждой задачи** (64 КиБ). Начальный кадр строится так,
чтобы `iretq` «вернулся» в `task_entry` с `RFLAGS=0x202` (IF=1) — задача
сразу исполняется с разрешёнными прерываниями и может быть вытеснена.

**Планировщик**: round-robin, состояния `Ready` / `Sleeping(до)` /
`Finished`, функции `spawn`, `sleep_ms`, `join`, `yield_now`, `list`.

## Две ошибки, которые пришлось найти

**1. #GP с кодом 0x10 при первом же переключении.** Расшифровка кода
ошибки указала на GDT-индекс 2 — селектор `0x10` (kernel data), который
я кладу в начальный кадр как SS. В GDT загрузчика есть только null и
kernel code; полную GDT ставит `usermode::init()`, а он вызывался
**после** планировщика. Переставил инициализацию: GDT/TSS теперь первыми.

**2. `Invalid opcode at 0x3` — перевёрнутый кадр.** Стек растёт вниз,
поэтому последнее записанное значение оказывается на вершине. Я
записывал регистры в том же порядке, в каком заглушка их снимает, — и
`pop r15` доставал то, что предназначалось для `rax`. Кадр нужно
заполнять в порядке, **обратном** `pop`-ам.

## Доказательство (serial-лог QEMU)

```
[sched] запуск 4 задач: 3 счётчика без yield + 1 спящая
[sched] итераций: worker-0=236, worker-1=240, worker-2=234
[sched] спящая задача проснулась 4 раз(а)
[sched] переключений контекста: 45
[sched] САМОПРОВЕРКА ПРОЙДЕНА: все задачи выполнялись одновременно
```

Ключевое: рабочие задачи — это `while` с инкрементом счётчика, **без
единого вызова yield, sleep или hlt**. Они физически не могут уступить
процессор сами. Раз счётчики всех трёх растут примерно одинаково —
значит их вытесняет таймер. Спящая задача отработала 4 цикла
`sleep_ms(50)`, то есть состояние `Sleeping` и пробуждение тоже рабочие.

Проверено и **после kexec**: в ядре, загруженном из `/kernel_a`,
самопроверки планировщика и Ring 3 проходят обе.

CLI: `threads [list|test]`.

## Честное ограничение

**SMP нет и не будет без APIC.** В ядре только PIC 8259; запуск
остальных процессоров требует IPI INIT/SIPI через LAPIC. Это настоящая
вытесняющая многозадачность **на одном ядре** — конкурентность без
параллелизма, как в Linux 2.0.

# Этап 7 — прослойка совместимости с Linux

Реализован запуск **настоящих ELF-программ Linux**. Не эмуляция и не
имитация: тестовая программа собрана системным `gcc` как статический
PIE, использует только Linux syscall ABI, и **тот же самый файл**
работает как на настоящем Linux, так и в DeiX.

## Что добавлено

`src/linux/elf.rs` — загрузчик ELF64: разбор заголовков, размещение
сегментов `PT_LOAD`, релокации `R_X86_64_RELATIVE` для PIE, подготовка
стека по System V ABI (argc/argv/envp/auxv).

`src/linux/syscall.rs` — Linux syscall ABI x86-64 с настоящими номерами
из `syscall_64.tbl`: `write`/`writev`, `brk`, `mmap`, `uname`,
`clock_gettime`, `getpid`/`getuid`/`getgid`, `nanosleep`, `getrandom`,
плюс безвредные заглушки инициализации libc (`arch_prctl`, `rseq`,
`set_tid_address`). Неизвестные номера возвращают `-ENOSYS`, как Linux.

Все указатели из Ring 3 проверяются на принадлежность пользовательской
области — иначе программа могла бы заставить ядро прочитать свою память.

## Три настоящих бага ядра, найденных при отладке

**1. `syscall_entry` не сохранял регистры.** Контракт Linux: инструкция
`syscall` портит **только** `rax`, `rcx` и `r11`; остальное программа
вправе считать неизменным. Мой обработчик перекладывал аргументы
(`rcx<-rdx, rdx<-rsi, rsi<-rdi, rdi<-rax`) и не восстанавливал их.
gcc держал номер вызова в `rdx` и перечитывал его для второго
`syscall` — программа получала мусорный номер `0x1800044`. Теперь
сохраняются `r8/r9/r10` и `rdi/rsi/rdx`.

**2. Старый `write` отвечал EFAULT.** Он проверял указатель против
страницы Ring 3 (`0x1400000`), а программы Linux живут по `0x1800000` —
вывод молча пропадал. Диспетчер переписан: `usermode` оставил себе
только `exit` и диагностику, всё остальное уходит в `linux::syscall`.

**3. Стек стоял ровно на границе области.** Первый же пролог
(`sub $0x190, %rsp`) уводил указатель за отображённую память.

## Доказательство (serial-лог QEMU)

```
[linux] linux_hello.elf: 2 сегм., точка входа 0x18001e5 (база 0x1800000)
  [prog] Здравствуй из настоящей программы Linux!
  [prog] getpid() = 1
  [prog] uname() -> DeiX
  [prog] brk() расширил кучу
  [prog] память из brk() доступна на запись
[linux] САМОПРОВЕРКА ПРОЙДЕНА (11 системных вызовов)
```

Программа печатает через `write`, получает `getpid()=1`, читает
`uname()` (ядро представляется как DeiX), расширяет кучу через `brk()`
и реально пишет в полученную память.

Все три самопроверки (`sched`, `linux`, `ring3`) проходят, загрузка
доходит до логина без исключений.

CLI: `linux run <файл>`, `linux info <файл>`, `linux test`.

## Честные ограничения

**`busybox` из Arch пока не запустится.** Он собран как `ET_EXEC` по
абсолютному адресу `0x400000`, где находится куча ядра. Переместить его
нельзя — адреса в коде абсолютные. Загрузчик отклоняет такие файлы с
внятным сообщением, а не падает.

Я пробовал поднять `.bss` ядра выше `0x400000`: 8, 12 и 14 МиБ
работают, 16 МиБ и выше — загрузка обрывается сразу после stage2
(причина в раннем коде загрузчика, не в подкачке). Это отдельная
задача, и я не стал выдавать её за решённую.

**Динамические бинарники** (`bash`, `ls`) требуют
`ld-linux-x86-64.so.2`, glibc и TLS — следующий большой этап.

Итог: прослойка работает и проверяема, но список запускаемого пока —
статические PIE. Путь к busybox: либо разобраться с ранней загрузкой и
освободить `0x400000`, либо пересобирать пакеты с `-static-pie`.

# Исправление: не работала клавиатура PS/2

Регрессию внёс я на этапе 4 (Ring 3), проявилась она после этапа 7.

## Диагноз

Замерил RFLAGS до и после самопроверки Ring 3:

```
[diag] RFLAGS=0x202 IF=1        <- до
[diag] ПОСЛЕ Ring3: RFLAGS=0x46 IF=0   <- после
```

Прерывания оставались **выключенными навсегда**. Отсюда и симптом:
IRQ1 (клавиатура), IRQ12 (мышь), IRQ0 (таймер) переставали приходить.
Ввод по COM1 при этом продолжал работать — он опрашивается в цикле, а
не по прерыванию, поэтому поломка бросалась в глаза только на PS/2.

Две причины, обе мои:

1. **`enter_ring3` задавал RFLAGS = `0x0002`**, то есть IF=0. Программа
   в Ring 3 исполнялась с запрещёнными прерываниями — её нельзя было
   даже вытеснить по таймеру.
2. **Выход через `exit` идёт не по `iretq`**, а через `mov rsp` + `jmp`,
   поэтому RFLAGS не восстанавливался автоматически. Нулевой IF
   «протекал» обратно в ядро.

## Исправление

* RFLAGS для Ring 3 теперь `0x0202` (IF=1) — как и должно быть: код
  пользователя обязан быть вытесняемым.
* В `ring3_return` добавлен явный `sti`.
* В `kernel_main` — страховка: если после самопроверок IF всё же сброшен,
  прерывания включаются принудительно с предупреждением в лог.

## Проверка

Не «должно работать», а замер. Через QEMU monitor отправлял настоящие
нажатия (`sendkey`) уже загруженной системе:

```
[IRQ1] скан-код 0x13   <- R нажата
[IRQ1] скан-код 0x93   <- R отпущена
[IRQ1] скан-код 0x1c   <- Enter нажат
[IRQ1] скан-код 0x9c   <- Enter отпущен
```

Обработчик IRQ1 получает скан-коды, контроллер PS/2 отвечает. Все три
самопроверки (`sched`, `linux`, `ring3`) проходят, исключений нет.
Диагностический вывод после проверки убран.

## Вывод на будущее

Ring 3 и прерывания надо проверять вместе: самопроверка «вернулись в
Ring 0» проходила успешно и **не замечала**, что система осталась без
прерываний. Теперь состояние IF проверяется явно.
