# Серверная активация dev-режима (Supabase)

Dev-режим DeiX (`dev on`) активируется через серверный реестр
устройств: заявка с машины → одобрение администратором → ключ
разблокировки. Данные лежат в проекте Supabase, а ОС ходит по HTTPS
(собственный TLS/HTTP-стек) на шлюз сайта `/api/os`, который сам вызывает
функции в Supabase. Ключей базы в ОС нет.

## Архитектура

```
ОС (dev link / dev request / фон-опрос)
        │  HTTPS, POST /api/os?fn=<функция>
        ▼
   сайт (web/api/os.js, Vercel) ── service_role (только env Vercel)
        ▼
   Supabase PostgREST ── RPC: begin_device_link, device_link_status,
                              request_dev_unlock, claim_dev_unlock
                         RPC (service_role): approve_dev_unlock, deny_dev_unlock,
                              link_device, unlink_device
                         таблицы dev_unlocks, device_links, dev_settings,
                         profiles (RLS, без политик)
```

* Шлюз пропускает от ОС только четыре функции (с проверкой Device ID и
  лимитом запросов на IP и устройство), к таблицам доступа нет: получить код привязки и его статус, подать заявку и забрать
  статус/токен.
* Заявку принимают только для устройства, привязанного к аккаунту:
  1. в ОС `dev link` печатает код XXXX-XXXX (10 минут);
  2. вошедший пользователь вводит его на сайте в «Аккаунт → Мои
     устройства» (до 5 устройств на аккаунт, неверные коды ограничены);
  3. ОС сама сообщает уведомлением, что привязка выполнена.
* Заявку подаёт ОС (`dev request`) или хозяин устройства на сайте
  (`/request`, устройство выбирается из привязанных). Владельцем заявки
  становится аккаунт, к которому привязано устройство.
* Владелец (роль `owner` в `public.profiles`) входит на сайт и открывает
  `/admin`: одобряет или отклоняет заявки, закрывает приём заявок. Одобрение генерирует токен в базе
  (`approve_dev_unlock`).
* Токен **одноразовый**: `claim_dev_unlock` отдаёт его устройству один
  раз, после чего строка получает статус `consumed`, а токен удаляется
  из таблицы. Если ОС не смогла сохранить полученный токен, владельцу
  нужно одобрить заявку заново (устройство подаёт её повторно).

## Настройка сервера

Схема применяется миграцией `supabase/migrations/20261017120000_dev_unlocks.sql`
(идемпотентна, доводит до нужной схемы и пустой проект, и таблицу-заготовку):

```sh
supabase link --project-ref xtsrvmwfnsxunvwuaplz
supabase db push
```

или целиком в Dashboard → SQL Editor. Привязка устройств —
`supabase/migrations/20261017200000_device_links.sql` (`public.device_links`).
Аккаунты сайта описаны миграцией
`supabase/migrations/20261017180000_accounts.sql` (`public.profiles`,
привязка заявок к `user_id`, функции для service_role).

Пользователи хранятся в Supabase Auth, имя и роль — в `public.profiles`.
Регистрация идёт через сайт: почта, username, пароль, повтор пароля и
капча Cloudflare Turnstile; почта проверяется на лету, а при настроенном почтовом ключе — письмом со ссылкой. Публичная
регистрация Supabase выключена (`disable_signup`), аккаунты создаёт только
серверная функция сайта.

Owner назначает триггер `handle_new_user` (миграция
`20261018120000_owner_claim.sql`): аккаунт, зарегистрированный с именем
`Atimenka`, получает роль `owner`, пока в `public.profiles` нет ни одного
owner. Пока owner не создан, имя может занять кто угодно, поэтому
регистрировать его нужно сразу. Допустим только один owner; при необходимости
роль можно выдать вручную:
`update public.profiles set role = 'owner' where lower(username) = lower('<логин>');`
Панель Owner открывается только в сессии с 2FA.

Сессия сайта — cookies `deix_at` (access-токен) и `deix_rt` (refresh),
`HttpOnly; Secure; SameSite=Strict`, 30 дней. Истёкший access-токен
сайт обновляет по refresh-токену сам.

Переменные окружения проекта Vercel (root directory `web`):
`SUPABASE_URL`, `SUPABASE_ANON_KEY` (publishable), `SUPABASE_SERVICE_ROLE_KEY`
(sensitive), `TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET` (sensitive; без них
капча отключена, и формы об этом предупреждают). Пароли в репозитории и env
не хранятся.

ОС собирается с одной публичной константой (`src/devauth.rs`): адрес
шлюза сайта. `service_role`, ключи Supabase и пароль Postgres в ОС не
попадают никогда.

## Если заявка не появилась

`dev request` печатает «request sent» только если сервер ответил
`created`. Иначе выводится причина:

* `HTTP 404 ... the site gateway does not know ...` — на Vercel задеплоена
  старая версия `web/`;
* `HTTP 401/403` — сайт отверг запрос (например, для проекта Vercel всё ещё
  включена Vercel Authentication);
* `HTTP 400: ...` — сообщение функции (например, приём заявок закрыт
  владельцем или слишком много ожидающих заявок);
* `server unreachable: Сервер не прислал ответа: <причина>; TCP принято N
  байт, TLS-записей M` — рукопожатие прошло, но ответа на запрос нет.
  Причина: таймаут, FIN или RST от сервера, TLS alert или ошибка
  расшифровки записи. Остальные `server unreachable` — DNS/TCP/TLS ошибки.
* `dev link` отвечает теми же сообщениями (функции `begin_device_link`).

## Офлайн-ключ с сайта (`dev unlock`)

Основной путь, не требующий сети в момент ввода.

1. В DeiX: `dev id` — печатает Device ID.
2. На сайте: «Аккаунт» → «Ключ разблокировки dev-режима» → вставить Device ID →
   «Получить ключ». Сервер подписывает `DEIX-DEV-UNLOCK-1 \0 || device_id || nonce`
   ключом ECDSA P-256 (закрытая часть — переменная `DEV_KEY_PRIVATE` на Vercel,
   base64 PKCS#8) и показывает ключ один раз: nonce (8 байт) и подпись (64 байта),
   base32, 116 символов, группы по 4.
3. В DeiX: `dev unlock <ключ>` (дефисы и регистр не важны), затем `dev on`.

ОС хранит только открытый ключ (`DEV_KEY_PUBLIC` в `src/devauth.rs`), проверяет
подпись для своего device_id и записывает использованный nonce в
`/userdata/etc/dev_keys.used`: тот же ключ повторно не принимается. Ключ
для другого устройства не пройдёт проверку. `dev revoke` снимает активацию, но
использованные ключи остаются использованными.

Лимит выдачи: 5 ключей в час на аккаунт; Owner может закрыть выдачу тем же
переключателем «приём заявок». В таблице `dev_keys` пишутся пользователь,
device_id и nonce (не сам ключ).

Честные границы: «одноразовость» проверяется локально, на этом устройстве
(переустановка /userdata её сбрасывает); сайт не знает, применён ли ключ.
Смена пары ключей: сгенерировать новую, обновить `DEV_KEY_PRIVATE` и
`DEV_KEY_PUBLIC` и пересобрать ОС; старые ключи перестанут работать.

## Сеть ОС: что сделано для ненадёжных каналов

* DNS возвращает до четырёх A-записей. `tcp::connect_any` пробует их по
  очереди; на каждый адрес SYN повторяется (при одном адресе — 15 с: 1, 2,
  4, 8 с, при нескольких — по 7 с). Ошибка называет причину по каждому
  адресу (RST или отсутствие SYN-ACK).
* Отправленные сегменты хранятся до подтверждения сервером и
  отправляются повторно (RTO 1 с, удвоение до 8 с, до 5 попыток).
* Приём проверяет seq: дубликаты отбрасываются, сегменты с пропуском не
  принимаются, на каждое отклонение уходит текущий ACK.
* ClientHello уходит двумя TCP-сегментами, разрезанными внутри имени
  хоста (SNI): против DPI, которое ищет имя в первом сегменте. Это одна
  техника из набора byedpi (split), а не сам byedpi; от блокировки по
  IP-адресу она не помогает.
* Ошибки запроса содержат стадию рукопожатия и сводку по соединению
  (отправлено/подтверждено байт, повторные отправки, дубликаты).

## Поток активации

1. **ОС**: `dev request` — генерирует `device_id` (32 hex-символа,
   `/userdata/etc/device.id`) и вызывает `request_dev_unlock`, после чего
   сразу закрывает соединение. Дальше статус раз в 20 с проверяет фоновый
   опрос из главного цикла (CLI/рабочий стол) вызовом `claim_dev_unlock`;
   при одобрении он сохраняет токен и показывает уведомление, при отказе —
   сообщает об отказе. После 5 сбоев связи подряд опрос прекращается.
   Входящего канала от сервера в ОС нет (slirp), поэтому «сервер
   сообщает» реализовано опросом.
   Вместо `dev request` можно выполнить `dev id` и подать заявку на сайте,
   затем `dev request` (или `dev on`) подхватит решение.
2. **Владелец**: в панели `/admin` одобряет или отклоняет заявку.
3. **ОС**: `dev on` — при наличии сохранённого токена работает офлайн, иначе
   вызывает `claim_dev_unlock`; при `approved` сохраняет токен в
   `/userdata/etc/dev_unlock.key` и включает dev-режим.

`dev off` выключает режим, но токен не удаляет; `dev revoke` удаляет
локальный токен (новая активация потребует новой заявки и одобрения).

## Честные границы (§42)

* Это **реестр устройств**, а не защита от владельца машины: исходники
  ОС открыты, любой может пропатчить проверку или выставить флаг в
  памяти. Никаких заявлений о «невзламываемости» код и документация
  не делают.
* Шлюз публичный: спросить код привязки и статус по Device ID может любой,
  кто знает Device ID (128 бит). Списка заявок и токенов он не даёт; заявку
  принимают только для привязанного устройства, одобряет только владелец
  проекта.
* Пароль Postgres и `service_role` дают полный контроль над базой —
  они не встраиваются в ОС, не публикуются и не передаются по каналам
  связи (пароль, однажды попавший в чат/лог, подлежит ротации).
