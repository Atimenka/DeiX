# Центр обновлений DeiX

Обновление ставится не на работающей системе и не патчем. ОС узнаёт о нём из
подписанного манифеста на сервере, скачивает сжатый пакет, перезагружается в
режим обновления и **целиком перезаписывает `/system`** (и загрузочный регион с
ядром, потому что `bootchain` сверяет их между собой). `/userdata` не
перезаписывается: он остаётся зашифрованным, а его данные преобразуются
операциями из манифеста. Схема с одним `/system`, без A/B-слотов.

## Что подписывается и чем проверяется

* Ключ — ECDSA P-256. Приватный ключ у владельца (`~/.deix/update_key.pem`),
  публичный (65 байт) вшивается в ядро из `build/update_pubkey.bin`.
* Подпись — над `sha256("DEIX-UPDATE-1\0" || манифест)`; манифест в каноническом
  JSON (ключи по алфавиту, без пробелов, только ASCII). ОС проверяет подпись
  теми же `crypto::ecdsa`, что и офлайн-ключ `dev unlock`.
* Манифест хранит `sha256` и размер нагрузки и `sha256` каждого сырого куска
  (по 512 КиБ). Сервер подпись не проверяет, а ОС не доверяет ни серверу, ни
  каналу: вся проверка в ОС.
* Нулевой публичный ключ = обновления в этой сборке выключены.

## Формат пакета

Файл `deix-update-<версия>.manifest`:

```
DEIXMANIFEST1
<подпись, 128 hex-символов (r||s)>
<манифест, одна строка канонического JSON>
```

Поля манифеста: `product` (`deix`), `version`, `build` (целое, растёт с каждым
коммитом), `min_build` (ниже — ставить нельзя, нужен промежуточный выпуск),
`channel` (`stable`/`beta`), `notes`, `schema` (целевая версия схемы
`/userdata`), `segments`, `chunk_sectors`, `chunks`, `payload_size`,
`payload_sha256`, `userdata_ops`.

Файл `deix-update-<версия>.payload` — последовательность записей
`u32 LE длина || gzip-член` (один член на 512 КиБ сырых данных). Распакованные
данные — подряд сегменты из `segments`:

| LBA | секторов | режим | что |
|-----|----------|-------|-----|
| 0 | 1 | `mbr` | только первые 446 байт (код MBR); таблица разделов диска остаётся |
| 1 | 2047 | `raw` | stage2, ramboot, ядро, дескриптор `DEIXKIMG` |
| 4096 | 20480 | `raw` | `/system` (EROFS) |

`build.sh` кладёт пакет в `build/update/`. Идентификатор сборки — время
HEAD-коммита (`git log -1 --format=%ct`); для несохранённых правок задайте
`DEIX_BUILD_ID`.

## Операции над /userdata

`userdata_ops` — список из `mkdir`, `remove` и `write` (данные — hex, до 1 КиБ)
с путями внутри `/userdata/`. Они выполняются в режиме обновления при открытом
томе и идемпотентны. Это не код: сложные преобразования ядро старой версии
выполнить не может — для них нужен промежуточный выпуск. После операций пишется
`/userdata/.deix-schema`. Реальных миграций пока нет: поле `schema` и файл
готовы, список операций пуст, пока формат данных не менялся.

## Порядок на устройстве

1. `update check` — GET манифеста, проверка подписи, сравнение `build`.
2. `update download` — скачивание кусками по 128 КиБ (лимит ответа ОС — 1 МиБ,
   таймаут 10 с), проверка `sha256`, запись в `/userdata/update/`. Свободное
   место заранее не проверяется: если его не хватает, запись падает с ошибкой,
   а недописанный пакет удаляется.
3. `update apply yes` — состояние «запрошено» в управляющем секторе
   (LBA 4000, вне разделов, не зашифрован) и перезагрузка.
4. Обычная загрузка до входа. Пока обновление ожидает, модули ядра не
   загружаются. Пароль вводится как всегда — он открывает том. После входа
   вместо рабочего стола запускается режим обновления: подпись и `sha256`
   проверяются заново, затем по порядку: `/system` → загрузочный регион
   (сначала сектора 1..2047, потом код MBR) → операции над `/userdata` →
   удаление пакета → перезагрузка.
5. Каждая фаза идемпотентна, состояние пишется после неё: после обрыва питания
   следующая загрузка продолжает с места остановки (режим обновления снова
   запускается после входа).

## Окно Updates на рабочем столе

Пункт «Updates» в меню Пуск и в Dock открывает то же самое, что команда
`update`, только кнопками: «Check now» → «Download» → «Install and restart».
Установка просит второе подтверждение с предупреждением о риске записи ядра,
после него запрос пишется в управляющий сектор и система перезагружается;
дальше всё идёт по порядку из раздела выше (пароль, режим обновления). «Discard»
удаляет скачанный пакет, «Cancel» снимает ожидающий запрос. Проверка сервера и
загрузка выполняются по одному блокирующему вызову за кадр, поэтому рабочий
стол между кусками перерисовывается; один вызов может занять до таймаута ОС
(10 с). Если сборка без ключа обновлений, это live-режим или `/system` в ext2,
окно показывает причину и не предлагает действий.

## Границы и риски

* **Окно записи ядра.** Между началом записи `/system` и концом записи
  загрузочного региона (несколько секунд) сырое ядро и `/system` не совпадают.
  Обрыв питания в этом окне оставляет систему, которая грузится с предупреждением
  `DX-KRN-0013` и продолжает обновление после входа. Обрыв **посреди записи
  самих секторов ядра/stage2** может сделать диск неботабельным; восстановление —
  переустановка. A/B-слотов нет по замыслу.
* Меняется геометрия загрузчика (размер stage2 → `KERNEL_LBA`): регион 1..2047
  и код MBR переписываются целиком и согласованно, но если разметка разделов
  в пакете другая, обновление невозможно — нужна переустановка.
* Пакет лежит на зашифрованном `/userdata` (отдельного раздела под него нет), и
  запись/чтение через XTS в эмуляторе без KVM медленные; время не измерено.
* Пакет читается в память целиком: предел нагрузки — 6 МиБ (куча ядра 16 МиБ).
* Обновление не работает в live-режиме с RAM-диска и если `/system`
  конвертирован в ext2.
* Режим обновления — тот же бинарник ядра, а не отдельная система: он не
  запускает рабочий стол, службы и оболочку, но загрузка до входа общая.

## Сервер

`GET /api/update?channel=stable` — подписанный манифест последней опубликованной
сборки; `GET /api/update?part=N&build=B` — N-й кусок нагрузки (128 КиБ).
Публикует Owner в `/admin` → «Обновления ОС»: загружает `.manifest` и
`.payload` из `build/update/`. Сервер хранит нагрузку в приватном бакете
`os-images` (`updates/<build>/`), лимиты — по IP.

## Сборка пакета одной командой

```
./make-update.sh --notes "что изменилось"
```

Скрипт создаёт ключ подписи при первом запуске (`~/.deix/update_key.pem`,
сделайте копию), вызывает `./build.sh` с этим ключом, упаковывает образ
`build/deix_disk.img` с вашими параметрами, проверяет пакет и печатает сводку.
Файлы `.manifest` и `.payload` лежат в `build/update/`. Параметры: `--channel`,
`--version`, `--min-build`, `--op`, `--schema`, `--build-id`, `--profile fast`,
`--out-dir`, `--no-build` (упаковать уже собранный образ; скрипт откажется,
если ядро в образе вшито с другим ключом или с другим build id). Справка —
`./make-update.sh --help`.

Содержимое манифеста: `python3 tools/make_update.py inspect --manifest <файл>
--key <ключ>` — сводка с проверкой подписи; с `--json` — полный JSON вместе с
подписью.

## Ключи

```
python3 tools/make_update.py keygen --key ~/.deix/update_key.pem
./build.sh
python3 tools/make_update.py verify --manifest build/update/deix-update-0.3.0-beta.manifest \
    --payload build/update/deix-update-0.3.0-beta.payload --key ~/.deix/update_key.pem
```

Потеря приватного ключа = невозможность выпускать обновления для уже
установленных систем (ключ вшит в ядро). Утечка = кто угодно может подписать
обновление: ключ нужно хранить так же, как `DEV_KEY_PRIVATE`.
